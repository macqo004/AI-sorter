# DOC-014 – Module Result Lifecycle and Cleanup

**Project:** AI Image Collection Management System

**Document:** DOC-014

**Version:** 1.0

**Status:** Design Specification

---

## 1. Purpose

This document defines the lifecycle of analysis results produced by independent project modules and the rules for invalidating and removing those results when the user wants to repeat an analysis using a changed model, algorithm, or module implementation.

The purpose is to keep module execution independent while avoiding unnecessary storage of multiple generations of the same module's results.

This document does **not** define file identity, database schema, individual analysis algorithms, or module execution order. Those responsibilities belong to the appropriate documents, especially DOC-005 and individual module specifications.

---

## 2. Core Principle

A module result belongs to a particular execution of that module against the current file identity and remains valid until the user deliberately requests that the result be cleared or replaced.

Changing a module's implementation, model, algorithm, thresholds, or other analysis logic does not automatically trigger a global reprocessing operation.

The system does not maintain multiple generations of module results merely to preserve historical model versions.

If the user wants results generated by a newer version of a module, the user is responsible for clearing the existing results for that module and running the module again.

---

## 3. Module Independence

Each analysis module maintains its own result state.

For example:

```text
IRL Filter       = PROCESSED
Screenshot Filter = PROCESSED
Universe Analysis = NOT_PROCESSED
Character Analysis = PROCESSED
```

This is a valid state.

Modules may be executed repeatedly and in any order, subject only to their explicitly documented prerequisites. The Scanner remains the base operation required to register newly discovered files in the database before those files can be analysed.

No module is required to wait for another unrelated module merely because the other module has not yet been executed.

---

## 4. Result Storage

Analysis results are stored in the database according to DOC-005.

A module result is associated with the current database representation of the file and the module's result state.

The fundamental file identity remains the SHA512 value defined by DOC-012.

Module Result Cleanup must never remove or alter:

* the file's SHA512 identity;
* the fundamental file record;
* the file path solely because an analysis result is cleared;
* unrelated module results;
* user decisions that are outside the selected module's result scope.

---

## 5. No Per-Result Model Versioning Requirement

The project does not require every analysis result to store a model or algorithm version identifier solely for the purpose of detecting stale results.

For example, the database does not need to retain:

```text
IRL result → model 1.0
IRL result → model 1.1
IRL result → model 1.2
```

The project intentionally avoids maintaining multiple generations of module results as a normal operating model.

This keeps the database simpler and prevents unnecessary growth of result metadata.

A module may maintain its own technical version information for diagnostics or compatibility where required, but DOC-014 does not require such information to be stored with every result.

---

## 6. Module Result Cleanup

When a module has changed sufficiently that its previous results should no longer be relied upon, the user shall use the Module Result Cleanup mechanism for that module.

Example:

```text
IRL Filter v1
    ↓
results exist in database
    ↓
IRL Filter updated to v2
    ↓
user wants a complete v2 analysis
    ↓
Clear IRL results
    ↓
Run IRL Filter again
```

Cleanup is explicitly user initiated.

The system must not silently clear millions of results merely because a program or model was updated.

---

## 7. Scope of Cleanup

Cleanup shall be scoped to one module or one explicitly selected result category at a time.

For example:

```text
Clear IRL results
```

must not automatically clear:

```text
Screenshot results
Universe results
Character results
Set results
```

unless the user explicitly selects those additional result sets and the relevant tool supports such a multi-module operation.

---

## 8. Cleanup Does Not Delete Files

Module Result Cleanup is a database-result operation.

It must not be interpreted as a file deletion operation.

For example:

```text
Before cleanup:

file.jpg
SHA512 = ABC...
IRL = FALSE
Universe = Genshin Impact
Character = Furina

After clearing IRL:

file.jpg
SHA512 = ABC...
IRL = NOT_PROCESSED
Universe = Genshin Impact
Character = Furina
```

The physical file remains untouched.

---

## 9. Cleanup and File Identity

SHA512 is the logical identity of the file content.

If a file is moved or renamed without changing its content, its SHA512 remains unchanged and its existing module results remain associated with that file identity.

If the file content changes and therefore its SHA512 changes, the resulting identity is different. Existing results belonging to the previous SHA512 must not be silently applied to the new content.

Module Result Cleanup is therefore not a substitute for the file identity and integrity mechanisms defined elsewhere.

---

## 10. Re-running a Module

After cleanup, the selected module treats the affected files as requiring processing again.

A normal execution may then process the files incrementally.

The module may also be interrupted and restarted. Already completed results must not require unrelated modules to be rerun.

Example:

```text
5,000,000 files

IRL cleanup
        ↓
IRL = NOT_PROCESSED
        ↓
IRL execution
        ↓
2,000,000 processed
        ↓
program stopped
        ↓
next execution
        ↓
continue remaining work
```

The exact execution and resume mechanism is defined by the module and execution documents, not by DOC-014.

---

## 11. User Responsibility

The user is responsible for deciding when existing module results should be discarded because a new version of the module should be applied to the collection.

The application should make this responsibility clear in the user interface and documentation.

It should not imply that changing a module automatically guarantees a full re-analysis.

Recommended user-facing warning:

```text
This module has been updated.
Existing results were generated by an earlier implementation.
If you want to recalculate the collection using the new implementation,
clear the existing results for this module and run it again.
```

---

## 12. Manual Decisions and Cleanup

Module Result Cleanup must not automatically erase independent user decisions.

In particular, a classification result that has been manually corrected by the user must not be treated as an ordinary stale result merely because another module is being cleaned.

Where a module's own result is explicitly cleared, the implementation must preserve any separate manual-decision state required by DOC-013 so that a later automatic execution cannot silently undo a protected user decision.

The exact interaction between analysis results and manual decisions is defined by the Review Queue and module-specific specifications.

---

## 13. Relationship with Scanner

Scanner registration is independent from Module Result Cleanup.

When a new file is discovered:

```text
Scanner
   ↓
file registered in database
   ↓
module result = NOT_PROCESSED
```

The module can subsequently analyse that file.

Clearing an existing module's results does not require the Scanner to recreate the file record.

---

## 14. Relationship with Database Maintenance

Module Result Cleanup is not a database rebuild.

It must not:

* recreate the file table;
* regenerate SHA512 values unnecessarily;
* remove unrelated files from the database;
* modify physical file locations;
* rebuild Collection Definition.

It is a targeted operation on the selected module's analysis results.

Database maintenance and integrity operations are defined separately.

---

## 15. Logging and Auditability

Every cleanup operation should be logged according to the project's logging rules.

The log should identify at least:

```text
execution_id
module
start time
completion time
number of affected results
completion status
errors, if any
```

A failed cleanup must not be reported as successful merely because part of the operation completed.

Where the database supports transactional cleanup for the selected result set, the implementation may use it. The exact transactional requirements belong to DOC-005 and the implementation specification.

---

## 16. Safety Rules

The following rules are mandatory:

1. Module Result Cleanup is explicitly user initiated.
2. Cleanup is scoped to the selected module/result set.
3. Cleanup does not delete physical files.
4. Cleanup does not remove the file's SHA512 identity.
5. Cleanup does not remove unrelated module results.
6. Changing a module does not automatically trigger global reprocessing.
7. The system does not require per-result model versioning solely to manage reprocessing.
8. User decisions protected by DOC-013 must not be silently undone by cleanup or subsequent automatic processing.

---

## 17. Example: Independent Module Updates

Assume the database contains:

```text
IRL            = processed
Screenshot     = processed
Universe       = processed
Character      = processed
Set Detection  = processed
```

The user installs a new IRL model.

The correct workflow is:

```text
1. User opens Module Result Cleanup.
2. User selects IRL Filter.
3. System reports the number of IRL results that will be cleared.
4. User confirms.
5. IRL results become NOT_PROCESSED.
6. Other module results remain unchanged.
7. User runs IRL Filter.
```

There is no requirement to rerun Screenshot, Universe, Character, or Set Detection merely because IRL changed.

---

## 18. Design Philosophy

The project deliberately prefers explicit user-controlled invalidation over automatic model-generation management.

This is consistent with the project's broader principles:

* modules are independent;
* the database is the shared state layer;
* the system should not perform expensive work unexpectedly;
* the user should remain in control of large-scale operations;
* the database should not grow indefinitely because old model generations are retained;
* expensive analysis should occur only when explicitly required.

---

## 19. Acceptance Criteria

DOC-014 is satisfied when the system provides a clear and safe mechanism that allows the user to:

* identify a module whose results should be recalculated;
* clear only that module's results;
* preserve file identity;
* preserve unrelated module results;
* preserve protected manual decisions;
* rerun the module after cleanup;
* perform the operation without deleting physical files;
* understand that changing a module does not automatically trigger reprocessing.
