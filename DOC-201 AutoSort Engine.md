AutoSort Engine

Project: AI Image Collection Management System
Document: DOC-201
Module: AutoSort Engine
Version: 1.0 Draft
Status: Design Specification

1. Purpose

AutoSort Engine is the decision and execution layer responsible for applying classification results generated by analysis modules to the physical file structure.

The module does not perform image analysis.

The module does not generate classifications.

The module only evaluates existing database information and applies configured sorting rules.

2. Core Philosophy

AutoSort Engine follows the principle:

AI provides observations. The database stores knowledge. AutoSort applies user-defined organisation rules.

The module SHALL NOT make independent AI decisions.

All actions SHALL be based on:

existing database records;
module confidence values;
configured thresholds;
existing folder structure;
user-defined priorities.
3. Responsibilities

AutoSort Engine SHALL:

evaluate classification results;
determine target location;
move files according to rules;
maintain one physical copy of each file;
prevent unwanted reclassification loops;
record performed actions;
support repeated execution.

AutoSort Engine SHALL NOT:

analyse images;
calculate SHA-512;
modify AI observations;
create duplicate files;
create shortcuts or hardlinks.
4. Single Physical File Rule

The system follows:

One image = one physical file = one canonical location.

A file SHALL never exist simultaneously in:

Universe tree;
Themes tree;
temporary trees;
category trees.

Alternative access methods such as:

shortcuts;
symbolic links;
hardlinks;
duplicated copies;

are intentionally not used.

5. Database as Source of Truth

The database is the authoritative source of classification information.

Folder structure is only a physical representation of database decisions.

Example:

Database:

Image:
SHA512 abc123

Universe:
Winx Club

Theme:
Fairy

Physical structure:

Themes/
└── Fairy/
    image.jpg

until a dedicated Universe folder exists.

6. Sorting Priority

Classification priority:

Universe
    |
    +-- Character

Theme

Universe always has higher priority than Theme.

7. Universe Sorting Rules
7.1 Existing Universe Folder

If:

Universe confidence >= threshold

AND

Universe folder exists

then:

move file to:

Universe/
└── Universe Name/

Example:

Database:

Universe:
Genshin Impact
Confidence:
0.98

Folder:

Universe/
└── Genshin Impact/

Result:

Universe/
└── Genshin Impact/
    image.jpg
7.2 Missing Universe Folder

If:

Universe detected

BUT

Universe folder does not exist

the file SHALL NOT be moved automatically to a newly created folder.

Reason:

Folder creation is a user decision.

The file remains in the current valid category.

Example:

Themes/
└── Fairy/
    image.jpg

Database:

Universe:
Winx Club

No folder:

Universe/
└── Winx Club/

Result:

No automatic move.

8. Universe Folder Creation Workflow

When the user creates:

Universe/
└── Winx Club/

AutoSort may be executed again.

The module SHALL then:

search database for matching Universe assignments;
locate affected files;
move files into the new Universe folder.

No AI processing is required.

9. Character Sorting Rules

Character sorting is subordinate to Universe sorting.

Character assignment requires:

Character confidence >= CharacterAssignmentThreshold

Default:

0.75

Example:

Universe:
Genshin Impact
Confidence:
0.98


Character:
Lumine
Confidence:
0.48

Result:

Genshin Impact/
image.jpg

NOT:

Genshin Impact/
└── Lumine/
10. Theme Sorting Rules

Theme is used when no higher priority destination exists.

Theme does not override Universe.

Example:

Image:

Furina wearing bikini

Database:

Universe:
Genshin Impact

Character:
Furina

Theme:
Bikini

Result:

Universe/
└── Genshin Impact/
    └── Furina/
        image.jpg

Theme information remains stored but does not create another physical copy.

11. TODO Tree Handling

TODO is treated as an unclassified workspace.

Files inside TODO may be processed repeatedly.

Manual rejection SHALL NOT permanently disable analysis.

Instead, rejection history SHALL influence future decisions.

Example:

Initial:

TODO/
image.jpg

AI:

IRL
0.90

Moved:

IRL/
image.jpg

User returns:

TODO/
image.jpg

The next analysis may run again.

However, the previous rejection should be recorded so the same automatic decision is not blindly repeated.

12. Manual Override Principle

Manual user actions have priority over automatic actions.

The system SHALL respect:

manual moves;
manual classification;
manual rejection.

Automatic sorting SHALL not continuously undo user corrections.

13. Rename Handling

AutoSort SHALL support filename conflicts.

The system SHALL NOT use default operating system behaviour:

filename (1).jpg

Preferred strategy:

filename_001.jpg
filename_002.jpg

or configurable naming rules.

14. Generic Filename Handling

Future versions MAY include automatic filename improvement.

Examples:

Before:

jndfsjdndnajndabfiaef.jpg

After:

Furina_Genshin_001.jpg

This functionality is outside the initial AutoSort scope.

15. Execution Modes

AutoSort supports:

Preview Mode

No files are moved.

Output:

planned actions

Example:

Move:
TODO/image.jpg

To:
Universe/Genshin Impact/
Execute Mode

Actions are physically performed.

Audit Mode

Checks:

database consistency;
missing files;
unexpected locations;
moved files.
16. Logging

Every operation SHALL be logged.

Example:

Timestamp:
2026-07-20 12:00

SHA512:
abc123

Action:
MOVE

Source:
Themes/Fairy/image.jpg

Destination:
Universe/Winx Club/image.jpg

Reason:
Universe folder created
17. Error Handling

If a move fails:

database SHALL not be updated as completed;
error SHALL be logged;
processing continues for other files.
18. Future Extensions

Possible future features:

automatic folder creation proposals;
user approval queues;
confidence-based batch moves;
duplicate cleanup;
collection statistics.
19. Acceptance Criteria

AutoSort Engine is considered complete when it can:

move files according to database information;
maintain one physical copy per image;
respect Universe priority;
use Theme as secondary organisation;
handle newly created Universe folders;
avoid classification loops;
preserve manual decisions;
execute safely in preview mode.
