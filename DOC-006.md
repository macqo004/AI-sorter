1. Purpose

This document defines the terminology used throughout the project.

Its purpose is to ensure that every document, source file and future module uses identical names for identical concepts.

This document introduces no functionality.

2. General Principles

The following rules apply throughout the project.

One concept shall have one official name.
Different concepts shall never share the same name.
Names shall remain stable once approved.
Internal names are written in English.
User interface language may be translated.
3. Image

Definition

A logical image known to the framework.

Image is the primary entity of the database.

It represents what the framework considers to be one image.

Image is independent of:

filename
directory
folder hierarchy
AI results
4. File

Definition

The physical file currently representing an Image.

A File may change location, filename or metadata.

Image identity remains unchanged.

5. Observation

Definition

Information produced by an analysis module.

An Observation represents what the framework has learned about an image.

Examples:

IsBW = True

Universe = Genshin Impact

Character = Furina

Theme = Halloween

Observation is not a user action.

Observation is not file metadata.

6. Feature

Definition

The type of information stored by an Observation.

Examples:

IsBW

IsIRL

IsScreenshot

Universe

Character

Theme

GroupImage

Feature names should be short, descriptive and stable.

7. Value

Definition

The value associated with a Feature.

Examples:

True

False

Furina

Genshin Impact

Halloween

Interpretation depends on the Feature.

8. Module

Definition

An independent executable component of the framework.

Each module performs exactly one well-defined task.

Examples:

Scanner

BW Filter

Screenshot Filter

Meme Filter

IRL Filter

Universe Detector

Modules communicate only through the database.

9. Job

Definition

One execution of one module.

Every module run creates exactly one Job.

A Job describes execution statistics.

It never describes an image.

10. Event

Definition

A historical record describing something that happened to an Image.

Examples:

Discovered

Moved

Renamed

ReturnedToTODO

Deleted

UserCorrected

Events are append-only.

11. Tag

Definition

A generic semantic label.

Tags are independent of folder hierarchy.

Examples:

Christmas

Beach

SchoolUniform

Night

Rain

Bikini
12. TODO Tree

Definition

Directory tree containing images awaiting processing.

Images in TODO are considered candidates for analysis.

Modules may process TODO multiple times.

13. AI Tree

Definition

Directory tree containing images automatically classified by the framework.

The AI Tree is a staging area.

It is not the final library.

14. Final Library

Definition

The user's manually curated image collection.

The framework treats this tree as authoritative.

Manual changes performed here may be used as feedback for future analysis.

15. Scanner

Definition

The module responsible for discovering files and synchronizing the database with the filesystem.

Scanner performs no semantic analysis.

16. Analysis Module

Definition

Any module that produces Observations.

Examples:

BW Filter
Screenshot Filter
Meme Filter
IRL Filter
Universe Detector

Analysis modules do not move files.

17. Feedback

Definition

Information inferred from user actions.

Examples:

moving an image,
correcting a classification,
returning an image to TODO.

Feedback may be used by future versions of the framework.

18. Classification

Definition

The process of assigning semantic information to an image.

Examples:

Universe

Character

Theme

Classification is represented in the database by Observations.

Classification is not a separate database entity.

19. Lifecycle State

Definition

The current status of an Image.

Initial values:

ACTIVE

MISSING

DELETED

ARCHIVED

Additional values may be introduced in future revisions.

20. Confidence

Definition

A numeric estimation of how confident a module is in its Observation.

Range:

0.0 – 1.0

Higher values indicate greater confidence.

21. Manual Correction

Definition

Any change made by the user that differs from the framework's previous decision.

Manual corrections are treated as authoritative.

22. Approved Document

Definition

A document whose architecture has been accepted.

Approved documents may receive:

typo corrections,
clarifications,
formatting improvements.

Approved documents must not receive architectural changes.

Architectural changes require a new revision or an RFC.

23. RFC (Request for Change)

Definition

A proposal introducing a structural modification to an approved document.

RFCs allow the project to evolve without continuously rewriting existing documentation.

24. Naming Rules

The following naming conventions apply.

Database entities:

PascalCase

Examples:

Image

Observation

Module

Database fields:

PascalCase

Examples:

ImageID

CurrentSHA512

ModuleID

ObservationTimestamp

Feature names:

PascalCase

Examples:

IsBW

IsIRL

GroupImage

Universe

Module names:

Human-readable English names.

Examples:

BW Filter

Scanner

Universe Detector
25. Project Philosophy

The framework is built around the following principles.

Modularity over complexity.
One module, one responsibility.
Database as the single source of truth.
User decisions have higher priority than AI decisions.
New functionality should be added by introducing new modules rather than modifying existing ones.
The framework is designed to solve real requirements rather than hypothetical future scenarios.
