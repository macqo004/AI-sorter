# Collection Definition Wizard – Architecture Update

**Project:** AI Image Collection Management System

**Document:** DOC-301 v1.1

**Applies to:** DOC-301

**Status:** Mandatory Update

---

# 1. Purpose

This document updates the Collection Definition Wizard described in DOC-301.

The update aligns Collection Definition with the storage model introduced in DOC-002A and the AutoSort changes introduced in DOC-201 v1.1.

This document supersedes any conflicting statements contained in DOC-301.

---

# 2. Source of Collection Structure

Collection Definition Wizard analyses **only the FINAL Collection Trees**.

The following areas are never used as sources for Collection Definition:

* TODO
* AI

FINAL is the only source of approved collection structure.

---

# 3. FINAL Collection Trees

The FINAL collection consists of one or more independent Collection Trees.

Current examples include:

```text id="m6fwl2"
Anime

Monster Girls

Western Animation

Themes
```

The Wizard treats each Collection Tree independently.

Additional Collection Trees may be added without modifying the Wizard.

---

# 4. Collection Definition Generation

During the initial configuration the Wizard:

1. scans the selected FINAL Collection Trees;
2. builds a temporary hierarchy;
3. presents the hierarchy to the user;
4. asks the user to define Classification Boundaries;
5. generates the Collection Definition.

No assumptions are made automatically.

---

# 5. Classification Boundary

A Classification Boundary defines the last directory belonging to the logical collection structure.

Everything below the boundary is considered user-managed organisation.

Example:

```text id="y0p6o3"
Anime
└── Games
    └── Hoyoverse
        └── Genshin Impact
            └── Furina   ← Boundary
                ├── 001
                ├── 002
                └── Favorites
```

Directories below the boundary are ignored by Collection Definition.

---

# 6. Boundary Selection

The Wizard provides an interactive interface allowing the user to choose the boundary.

Example:

```text id="e7mtwq"
Anime
└── Games
    └── Hoyoverse
        └── Genshin Impact
            └── Furina
```

User action:

```text id="n6m0wv"
✓ Mark Furina as Classification Boundary
```

Only explicit user confirmation creates a boundary.

---

# 7. Boundary Types

Each Classification Boundary has a logical type.

Examples:

Character

```text id="2jpcl2"
Anime
└── Genshin Impact
    └── Furina
```

Species

```text id="mjlwmu"
Monster Girls
└── Angel
```

Universe

```text id="s8w9ef"
Western Animation
└── Disney
```

Theme

```text id="jlwm3x"
Themes
└── Bikini
```

The boundary type is stored as part of Collection Definition.

---

# 8. Update Behaviour

During future executions the Wizard performs incremental updates.

Previously defined Classification Boundaries are treated as terminal nodes.

The Wizard does not scan directories located below an existing boundary.

Example:

Existing definition:

```text id="mqr0xw"
Anime
└── Games
    └── Hoyoverse
        └── Genshin Impact
            └── Furina   ← Boundary
```

Current directory:

```text id="6pp5n2"
Furina
├── 001
├── 002
├── 003
└── New Set
```

The Wizard ignores:

* 001
* 002
* 003
* New Set

No update is generated.

---

# 9. Detection of New Branches

Only previously unknown branches are analysed.

Example:

Existing Collection Definition:

```text id="h3bn6q"
Anime
└── Games
    └── Hoyoverse
```

Filesystem:

```text id="ivp6ko"
Anime
└── Games
    └── Hoyoverse
        ├── Genshin Impact
        └── Zenless Zone Zero
```

The Wizard analyses only:

```text id="jlwm1p"
Zenless Zone Zero
```

Previously configured branches remain untouched.

---

# 10. User Confirmation

Every newly detected branch requires explicit confirmation.

The Wizard never automatically:

* creates Classification Boundaries;
* assigns boundary types;
* expands Collection Definition.

---

# 11. Relationship with AutoSort

AutoSort uses Collection Definition as the only source of destination structure.

Collection Definition therefore determines every valid destination available to AutoSort.

If a destination is absent from Collection Definition, AutoSort treats it as unavailable.

---

# 12. Relationship with Collection Consistency Checker

Collection Consistency Checker also relies on Collection Definition.

Migration suggestions are generated only for destinations defined inside Collection Definition.

Unknown destinations are ignored.

---

# 13. Design Principles

Collection Definition Wizard:

* analyses FINAL only;
* ignores TODO;
* ignores AI;
* never analyses below existing Classification Boundaries;
* never guesses user intentions;
* requires explicit confirmation for every new branch;
* preserves all previously approved boundaries.

---

# 14. Acceptance Criteria

The update is considered complete when:

* Collection Definition is generated exclusively from FINAL;
* Classification Boundaries are user-defined;
* existing boundaries prevent deeper scans;
* only new branches are analysed during updates;
* AutoSort and Collection Consistency Checker rely exclusively on Collection Definition.
