1. Purpose

This document defines the core database entities used by the framework.

The schema is designed around the lifecycle of an image and the knowledge accumulated about it.

The database must support millions of images while remaining extensible without requiring structural redesign when new analysis modules are introduced.

2. Entity Overview
Image
 │
 ├── File
 │
 ├── Observation
 │
 ├── Event
 │
 └── Tag (defined in Part B.2)

Image is the root entity.

Every other entity references Image.

3. Entity: Image
Purpose

Represents one logical image known to the framework.

Image is independent from:

filename
directory
extension
AI classification
filesystem location

The Image entity exists even if the physical file is temporarily unavailable.

Ownership

Created by:

Scanner

Modified by:

Database maintenance only

Normal framework modules MUST NOT modify Image records.

Fields
ImageID

Type

INTEGER (64-bit)

Properties

Primary Key
Auto Increment
Unique
Immutable

Purpose

Permanent logical identifier used throughout the framework.

CurrentSHA512

Type

TEXT

Length

128 hexadecimal characters

Properties

Unique
Indexed

Purpose

Stores the SHA-512 hash of the current binary representation of the image.

Changing filename or directory MUST NOT modify this value.

Changing the image content MAY update this value.

FirstSeen

Type

DATETIME

Purpose

Timestamp when the image first entered the framework.

Immutable.

LastSeen

Type

DATETIME

Purpose

Timestamp of the latest successful filesystem verification.

Updated by Scanner.

LifecycleState

Type

ENUM

Initial values

ACTIVE
MISSING
DELETED
ARCHIVED

Purpose

Represents the current lifecycle state of the image.

Future values MAY be added.

Design Notes

The Image entity intentionally stores very little information.

Its responsibility is identity.

All metadata belongs to specialized entities.

5. Entity: Observation
Purpose

Stores every observation produced by analysis modules.

Observation contains knowledge generated by the framework.

It does not contain:

filesystem metadata
user actions
file history
module execution history
Philosophy

Modules never add columns.

Modules add observations.

Every new module uses the same structure regardless of what it detects.

Ownership

Created by:

Analysis modules.

Modified by:

The module that created the observation.

Other modules MUST NOT overwrite observations created by another module.

Design Notes

Observation is intentionally generic.

Adding a new module MUST NOT require:

database migration
schema redesign
adding new columns
adding new tables

New functionality should be represented by new observations.

6. General Rules
Every entity references Image.
Image references no other entity.
File contains only filesystem information.
Observation contains only analytical results.
Scanner never performs semantic analysis.
Analysis modules never move files.
Filesystem modules never classify images.
Each entity owns exactly one responsibility.
7. Scalability Requirements

The schema MUST support:

Initial target:

5,000,000 images

Expected target:

20,000,000+ images

Adding a new module MUST NOT require schema modification.

Adding a new Feature MUST NOT require schema modification.

Database migrations should remain exceptional events rather than normal development practice.
